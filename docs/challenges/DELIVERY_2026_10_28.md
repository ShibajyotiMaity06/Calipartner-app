# Challenges and pair onboarding delivery — 28 October 2026

1. **What was built**

   Completed the owner-approved CH-0 audit and CH-1 through CH-7 implementation. Challenges now use a database catalogue, actual profiles and logging records instead of sample people, invented progress or participant counts. The catalogue contains 14 templates, six formats and three dated seasons. Winter Arc opens first, on 1 December 2026; upcoming seasons offer real reminders rather than fake live participation.

   The shared core evaluates personal baselines, safe metric bounds, daily caps, weekly rhythm, checklist tasks, total/duel/co-op progress, pauses, shields, partner cover, event-week adjustments and results. Rules and joining benefits are captured per challenge. Finalization uses server time, the participant's stored timezone and the configured sync window. Finalized history survives late edits. Optional body milestones use the existing rate and BMI safeguards; weights remain private to their owner.

   Added authenticated creation/acceptance, separate plan allowances, room-host checks, privacy-safe projections, comparison opt-out, reporting/blocking, capped encouragement/reminders, an activity feed, quiet-hour-aware notifications, Realtime updates and polling. Account-scoped SQLite caches and idempotent outboxes preserve offline actions. Added seasonal boards with consent and minimum public counts, editable occasion habits, milestones, trophies, earned chapter share frames, real-stat PNG sharing and the purchased-Pro AI recap hook. The recap endpoint sends only the selected summary and retains the existing AI consent, budget and daily usage gates. The admin dashboard is restricted by trusted Auth `app_metadata.challenge_admin`.

   Added the pair invitation screen immediately after signed-in onboarding, with “1-on-1 is free”. Sharing allocates no room. Explicit acceptance creates the pair and consumes exactly one hosted-room slot for the inviter. Invite links survive signup and onboarding. Room challenges link to the unified feature; existing room challenge history is preserved.

   Integration tests also exposed two existing failures required for these flows: the workout push trigger referenced `title` instead of the canonical `name`, and account-deletion cascades could recreate daily summaries for an account being deleted. Both have migration-backed repairs. Disposable test participation is removed from counters on deletion.

4. **Assumptions adopted**

   Used the plan's recommended defaults as editable seed configuration: separate Free solo/pair allowances, one Free solo season, a personal seasonal clock, opt-in public boards and non-monetary promises. Free starter durations are at most the configured allowance; Weekend Warrior remains the configured two-day starter. Paid benefits captured when joining continue through a lapse; new creation uses current entitlements.

   “Forced pair onboarding” means the invitation screen is always presented next, while “Continue solo” preserves access for users without an available buddy and for offline logging. The hosted allowance belongs to the inviter; joining does not consume the recipient's unused hosting allowance.

5. **Deployment and manual steps**

   All challenge migrations and both Edge handlers are deployed to the linked Supabase project. The hourly challenge schedule is active. Its dedicated secret and URL are configured privately; cron requests use a short-lived HMAC. No secret is included in application code, this report or the repository.

   Create a fresh EAS development build to include the new Expo Sharing native module. Earlier development binaries fall back to text sharing. Android/iOS exports validate bundling, but a real-phone walkthrough still needs a connected device. To use `/dev/challenges`, a trusted administrator must set `challenge_admin: true` in their own Auth **app_metadata**, never client-editable user metadata.

   The disposable accounts, rooms, challenge instances, growth analytics and rate-limit fixtures are cleaned up after the final hosted/browser checks. Public participation is recalculated from retained real records; dummy accounts do not inflate it.
